# المتحدة للخدمات التعليمية — دليل التحويل إلى النظام المركزي (v3.0.0)

## ما الذي تغير بالفعل؟

- توجد الآن نسخة خادم مركزية `backend/cloud/app.py` بدلاً من تشغيل خادم SQLite منفصل في كل جهاز.
- قاعدة الإنتاج المستهدفة **PostgreSQL** على Railway أو أي خادم PostgreSQL مؤمّن، والواجهات تتواصل معه بواسطة HTTPS.
- تطبيق Electron أصبح عميلًا خفيفًا؛ لا ينسخ قاعدة بيانات إلى جهاز الموظف ولا يثبت Python على أجهزة العاملين.
- شاشة إعداد تظهر أول مرة وتطلب **عنوان تطبيق المتحدة HTTPS** (وليس اسم/كلمة مرور قاعدة البيانات).
- الحسابات والصلاحيات والتحقق من الجلسات تتم على السيرفر. لا يمكن للسيلز الترقية إلى مالك بمجرد تغيير الواجهة.
- مزامنة بيانات العملاء والمشروعات تتم بالتغييرات على مستوى السجل، مع إظهار تعارض التعديلات. توجد إشعارات WebSocket مع فحص دوري كل 7 ثوانٍ.
- المدفوعات تتطلب API مخصصًا لموظف مالية مخوّل، ولا تقبل من حفظ الواجهة العام.

**ما لم يحدث:** لم يتم إنشاء سيرفر Railway داخل حسابك، ولم يتم نقل قاعدة بيانات جهازك الحقيقية إلى الإنترنت، ولم يتم بناء EXE أو اختبار نظام الإنتاج على Windows. هذه حزمة كود جاهزة لمرحلة الربط والنشر والاختبار، وليست إعلان جاهزية إنتاجية نهائية.

## المرحلة الأولى — الحصول على نسخة دقيقة من بيانات جهازك

1. أغلق نسخة UES v2.5.2 المحلية تمامًا.
2. اضغط `Win + R` والصق: `%APPDATA%\UES SMART ERP\data`.
3. انسخ `ues_smart_erp.db` إلى مجلد خاص، مثل `D:\UES_Backup\ues_smart_erp.db`.
4. احتفظ بالملف الأصلي دون تغيير. **البيانات التي أرفقتها في المحادثة كانت بيانات نموذجية وقد تختلف عن ملف جهازك.**
5. لا ترسل قاعدة البيانات لأي جهة خارجية دون التحقق من حماية بيانات العملاء.

## المرحلة الثانية — إنشاء خدمة PostgreSQL وخادم API

1. افتح https://railway.com وسجل الدخول.
2. أنشئ `New Project` ثم `PostgreSQL`.
3. ارفع محتويات الحزمة إلى GitHub **Private Repository** باسم `UES-SMART-ERP` (تجنب رفع أي ملف بيانات حقيقية أو مفاتيح).
4. داخل مشروع Railway، أضف خدمة من المستودع واختر المشروع. سيستخدم `railway.json` ملف `deployment/Dockerfile`.
5. من خدمة تطبيق API في Railway، اضبط متغيرات البيئة:

   - `DATABASE_URL` = مرجع `DATABASE_URL` لقاعدة PostgreSQL في نفس مشروع Railway (يظهر من قسم Variables؛ لا تضعه في HTML أو EXE).
   - `UES_PUBLIC_URL` = `https://YOUR-UES-SERVER.up.railway.app` (استبدل باسم رابط تطبيقك الفعلي).
   - `UES_ALLOWED_HOSTS` = `YOUR-UES-SERVER.up.railway.app` (اسم المضيف فقط دون https).
   - `UES_TRUST_PROXY` = `true` (مخصّص للتوثيق، لكن التطبيق يعتمد على UES_PUBLIC_URL في الكوكيز والتحقق من Origin؛ لا تعطل TLS).

6. خصص Public Domain بخدمة API، وفعل Healthcheck Path: `/api/health`.
7. افتح `https://YOUR-UES-SERVER.up.railway.app/api/health` وتحقق من:

   `"service":"UES-SMART-ERP-CENTRAL"` و`"database":"postgresql"`.

تكون قاعدة البيانات فارغة في أول نشر؛ شاشة الدخول لن تعمل حتى تستورد بيانات مؤسسة ومالك أو تضيفهم وفق إجراء إعداد موثوق.

## المرحلة الثالثة — فحص SQLite دون نقل (موصى به دائمًا)

على كمبيوتر آمن به Python 3.12+ ومن داخل مجلد المشروع، شغّل:

```powershell
py -3 -m pip install -r backend\cloud\requirements.txt
py -3 scripts\migrate_sqlite_to_postgres.py --sqlite "D:\UES_Backup\ues_smart_erp.db" --include-ui-snapshot --report migration_report.json
```

هذا أمر **Dry Run**: يقرأ السجلات ويكتب تقريرًا ولا يتصل بـPostgreSQL ولا يغيّر ملف SQLite.

افتح `migration_report.json` وراجع أعداد العملاء والمشروعات والفواتير. بعض التعديلات في النسخة القديمة قد تكون في جدول `desktop_ui_state`، لذلك يتطلب دمجها علم `--include-ui-snapshot`. لا يستبدل هذا العلم سجلات الهوية أو المدفوعات والفواتير غير المتحققة، ويجب مراجعتها مع المسؤول المالي بعد الترحيل.

## المرحلة الرابعة — النقل مرة واحدة إلى PostgreSQL الفارغة

1. من إعدادات Railway، احصل على **DATABASE_PUBLIC_URL** مؤقتًا بطريقة آمنة لجهاز الترحيل، أو نفذ أداة الترحيل في بيئة خاصة متصلة بقاعدة Railway؛ احذر من نشر الرابط في محادثات أو لقطات شاشة.
2. أنشئ ملفًا خاصًا `D:\UES_Backup\new_owner_password.txt` يحتوي على كلمة مرور قوية **جديدة** للمالك، 14 حرفًا على الأقل. احتفظ به خارج مجلد المشروع ثم احذفه بعد التأكد من الدخول.
3. افتح PowerShell واضبط متغير `DATABASE_URL` لجلسة الترحيل فقط (لا تنسخه داخل كود، ولا ترسله لنا):

```powershell
$env:DATABASE_URL="postgresql+psycopg://USERNAME:PASSWORD@HOST:PORT/DATABASE?sslmode=require"
py -3 scripts\migrate_sqlite_to_postgres.py --sqlite "D:\UES_Backup\ues_smart_erp.db" --include-ui-snapshot --apply --owner-username Ahmed_99 --owner-password-file "D:\UES_Backup\new_owner_password.txt" --report migration_applied.json
```

**حماية أساسية:** الأداة ترفض النقل إذا كانت قاعدة الإنتاج تحتوي بيانات مسبقة، وتجعل كل حساب غير المالك غير نشط، وتستبدل كلمات المرور القديمة كلها. المالك يسجل بكلمة المرور الجديدة ثم ينشئ/يعيد تفعيل حسابات الموظفين مع كلمات جديدة وفق الحاجة. لا تنقل قواعد متعددة فوق بعضها.

## المرحلة الخامسة — إنشاء Setup ويندوز وإعداد الموظفين

1. ثبت Node.js LTS على جهاز البناء.
2. افتح مجلد المشروع في VS Code.
3. اضغط مزدوجًا على `BUILD_CENTRAL_WINDOWS_EXE.bat` أو نفذ:

```powershell
npm.cmd install
npm.cmd run build:windows
```

عند نجاح البناء سيكون الملف المتوقع:

`release\UES-Smart-ERP-Central-Setup-3.0.0.exe`

ثبت البرنامج على جهازك وجهاز الموظف. عند الفتح الأول سيطلب **رابط سيرفر المتحدة HTTPS**. ضع نفس الرابط على كل الأجهزة. بعدها كل موظف يستخدم حسابه الخاص. لا يُطلب على أجهزة الموظفين تثبيت Python ولا إدخال بيانات PostgreSQL.

## المرحلة السادسة — اختبار جهازين قبل استخدام العمل الحقيقي

1. ادخل بصلاحية المالك على الجهاز الأول وبصلاحية Sales على الجهاز الثاني.
2. أضف عميلًا تجريبيًا من جهاز Sales، وانتظر بضع ثوانٍ ليظهر عند المالك؛ يمكن تحديث الشاشة يدويًا عند الحاجة.
3. عدل العميل على الجهازين في نفس الوقت، واختبر ظهور إشعار تعارض بدل فقد تحديث أحدهما.
4. تأكد أن Sales لا يقدر على حذف الأدوار أو استخدام API المالية مباشرة.
5. جرّب حساب Finance لتأكيد دفعة اختبارية منفصلة، ثم تأكد من رفض المرجع المالي المكرر.
6. غيّر دور أحد الموظفين من السيرفر أو عطّل حسابه، وتحقق من تأثير التغيير على الطلبات التالية (التحقق من جلسة المستخدم يتم في كل طلب).
7. اختبر إعادة فتح البرنامج، وانقطاع اتصال الإنترنت، وإجراءات النسخ الاحتياطي والاستعادة.

## تنبيه تشغيلي وأمني

- النسخة الجديدة لا تحتوي رابط سيرفر حقيقي؛ ستُدخل الرابط بعد نشر الخدمة.
- لا تشارك DATABASE_URL أو ملفات النسخ الاحتياطية الحقيقية أو ملفات كلمات المرور.
- نظام AI الحالي محاكاة؛ لا يوجد ربط مباشر جاهز بأكاونت ChatGPT أو برسائل واتساب.
- القيم التجارية المعتمدة والقوالب المالية لا تزال تحتاج مراجعة، ولا يجوز استخدام تدفقات الدفع التجريبية لإثبات وصول أموال فعلية.
- PostgreSQL المركزي متاح من الخادم فقط. لا تستخدم مشاركة ملف SQLite على OneDrive أو Google Drive كبديل.
- تمت مراجعة واختبار عدة مسارات API محليًا على SQLite اختبارية. لم يتم التحقق من نشر Railway أو تشغيل PostgreSQL البعيدة أو برنامج Windows EXE في بيئتنا؛ اختبرها قبل التشغيل التجاري.
